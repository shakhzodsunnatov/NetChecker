# API Flows — сценарии из связанных запросов

**Дата:** 2026-08-04
**Статус:** реализовано
**Релиз:** 2.1.0
**Реализация:** ветка `feature/api-flows`, план — `docs/superpowers/plans/2026-08-04-api-flows.md`

> **Настройка шага реализована.** Зависимости, условие, извлечение и подстановка
> значений, проверка статуса и пауза задаются из интерфейса — экран открывается
> из карточки шага. Параллельность и развилки собираются там же: порядок
> определяется зависимостями, отдельного режима нет.
>
> Редактор по тапу именно на проводе (§4.4) не делался: связь принадлежит паре
> шагов, а строка графа может содержать несколько узлов, поэтому тап по проводу
> неоднозначен. Настройка живёт на шаге, где она недвусмысленна.

---

## 1. Задача

Новая функция приложения обычно состоит из нескольких связанных вызовов. Четвёртый нельзя проверить в отрыве от первых трёх: логин отдаёт токен, создание заказа — его идентификатор, и только потом имеет смысл оплата.

Сегодня, чтобы проверить такую цепочку и дать её проверить бэкенд-разработчику, приходится собирать мок-сцену в коде приложения и выкладывать сборку в TestFlight. Долго, и на каждое изменение цикл повторяется.

**Flows** дают собрать сценарий из уже пойманных запросов и прогнать его одной кнопкой, не трогая код приложения.

---

## 2. Модель выполнения

Сценарий — направленный ациклический граф шагов. Не линейная цепочка: пользователю нужны параллельные ветки и развилки.

### 2.1 Когда шаг запускается

Шаг стартует, когда завершились **все шаги, от которых он зависит**, и его условие истинно.

Из одного этого правила выводятся все затребованные случаи:

| Случай | Как выражается |
|---|---|
| Строгая последовательность | у каждого шага одна входящая связь от предыдущего |
| Шаги 1 и 2 параллельно | ни у одного нет входящих связей |
| Шаг 3 ждёт обоих | у шага 3 входящие связи от 1 и 2 |
| Шаг 3 ждёт только 2, шаг 1 просто отрабатывает | у шага 3 одна связь — от 2; шаг 1 стартует одновременно, но его никто не ждёт |

Отдельного переключателя «параллельно / последовательно» нет. Порядок задаётся связями, и одно правило описывает все режимы.

**Шаг-триггер** — шаг, от которого никто не зависит. Отправляется и не задерживает прогон. В интерфейсе помечен как «не ждём»: иначе непонятно, почему сценарий завершился, пока такой запрос ещё летит.

### 2.2 Условия

У шага может быть условие. Ложное условие означает **пропуск**, а не ошибку: прогон продолжается.

Условие хранится **на шаге**, а рисуется **на входящей связи**. Хранить на шаге проще — не нужно заводить сущность «ребро с логикой»; рисовать на связи правильнее — так это читается как развилка.

If / else выражается двумя шагами от одного родителя: у первого условие `total > 0`, у второго — `иначе`. Ровно один выполнится.

Операнды: значение из ответа любого **уже завершившегося** шага, либо константа.
Операторы: `==`, `!=`, `>`, `<`, `истина`, `ложь`, `существует`, `пусто`.

Шаги, зависящие от пропущенного, пропускаются каскадом — если у них нет другой выполненной зависимости.

### 2.3 Передача значений

Шаг объявляет **выходы** — что извлечь из ответа, и **входы** — куда подставить.

- Извлечение: JSON-путь по телу ответа либо заголовок ответа.
- Подстановка: заголовок, сегмент пути (`/orders/{orderId}/pay`), query-параметр или поле тела.

Одна связь может нести несколько значений; шаг может брать значения из нескольких предыдущих.

**Если значение не найдено, шаг падает** с текстом «поле `orderId` отсутствует в ответе шага 2». Уходить в сеть с пустой подстановкой нельзя: получится неверный запрос и непонятная ошибка от сервера.

### 2.4 Проверки

У шага может быть ожидаемый статус. Ответ, не совпавший с ожиданием, — ошибка шага. Это превращает сценарий из набора вызовов в проверку.

---

## 3. Поведение при ошибке

Падение шага **останавливает прогон**. Зависящие шаги не запускаются и помечаются «не запускался». Если бы цепочка шла дальше, посыпались бы все последующие и стало бы неясно, что сломалось на самом деле.

Параллельные ветки, не зависящие от упавшего шага, доводятся до конца — их падение не касается.

### Восстановление

**Значения, собранные завершившимися шагами, сохраняются в контексте прогона.** Это ключевое требование: повтор не должен начинать с логина.

Доступно на упавшем шаге:

| Действие | Что делает |
|---|---|
| Повторить с шага N | Перезапускает только этот шаг и продолжает граф. Контекст сохранён. |
| Изменить | Открывает шаг в редакторе запроса; после правки запуск с того же места. |
| Пропустить шаг | Помечает пропущенным и идёт дальше — когда падение ожидаемо. |
| Начать заново | Сбрасывает контекст и прогоняет с нуля. |

Разбор упавшего шага показывает статус, тело ответа, длительность и **что именно подставилось** (`orderId = 7781`, `token = eyJh…9c`). Ломается обычно подстановка, а не сам запрос.

## 4. Интерфейс

### 4.1 Раскладка

Отдельная вкладка инспектора **Flows**, скрываемая как остальные разделы.

Граф рисуется уровнями: **строка = уровень выполнения**, всё в строке идёт одновременно. Уровни вычисляются из связей — раскладку не задают руками, перетаскивания нет.

Это снимает главную проблему графов на телефоне: прокрутка только вертикальная, зума и панорамы по двум осям нет. При ширине 375 pt два узла в строке — по 158 pt каждый. Три и больше — строка прокручивается вбок внутри себя, остальной экран неподвижен.

### 4.2 Связи

Провода рисуются **только между соседними уровнями**. Если шаг 6 берёт токен из шага 1, длинная дуга через полэкрана не рисуется — вместо неё внутри узла появляется строка `← token из 1`.

Так видна каждая зависимость, но полотно не превращается в клубок, и сразу читается, чем узел питается.

На проводе перечисляются имена значений: `orderId · total`. Больше двух — `orderId +2`, тап открывает полный список.

### 4.3 Состояния узла

| Состояние | Вид |
|---|---|
| Ожидает | приглушён, серый номер |
| Выполняется | синяя обводка, увеличен через `scale` |
| Успех | зелёная обводка, галочка |
| Ошибка | красная обводка, код ответа |
| Пропущен | пунктир, приглушён, подпись условия |
| Триггер | оранжевый пунктир, метка «не ждём» |

Состояние передаётся не только цветом — есть значок, номер и текст.

### 4.4 Тап

- **узел** — карточка шага: запрос, ответ, подставленные значения, действия восстановления
- **провод** — редактор связи: откуда берём и куда кладём
- **＋** — добавление шагов: список пойманного трафика с множественным выбором, тем же жестом, что и пометка тегами

### 4.5 Сборка сценария

Основной способ — выбрать запросы из уже пойманного трафика: тот же экран множественного выбора, что и у тегов. Выбранные добавляются в порядке отметки, каждый со всеми своими заголовками и телом.

Помеченные тегом запросы можно добавить целиком — тег и сценарий описывают одну и ту же группу вызовов.

### 4.6 Анимация

Заливка провода и рост активного узла — пружиной, 150–300 мс. Активный шаг увеличивается через `scale`, а не изменением размеров: соседи не съезжают.

При включённом «уменьшении движения» пружины заменяются мгновенной сменой цвета.

## 5. Прочее

**Окружение.** Сценарий не хранит хост — прогон идёт через активное окружение. Переключили на staging, тот же сценарий проверил staging. Токен окружения подставляется как обычно.

**Экспорт.** Сценарий сериализуется в файл и открывается на другом устройстве. Это снимает исходную боль целиком: вместо сборки в TestFlight ради бэкендера — отправленный файл, который он запускает у себя.

**Пауза между шагами.** Задаётся на шаге. Некоторым бэкендам нужно время, чтобы предыдущее действие доехало до очереди.

**Хранение.** Сценарии переживают перезапуск приложения, лежат в `UserDefaults` рядом с прочими настройками SDK.

## 6. Состав кода

```
Sources/NetCheckerTraffic/Flows/
  FlowStep.swift          # шаг: запрос, зависимости, условие, входы, выходы
  FlowCondition.swift     # операнды и операторы
  FlowValueBinding.swift  # извлечение и подстановка значений
  Flow.swift              # сценарий, вычисление уровней, проверка на циклы
  FlowStore.swift         # хранение и персистентность
  FlowRunner.swift        # выполнение графа, контекст, восстановление
  FlowExporter.swift      # сериализация

Sources/NetCheckerTrafficUI/Flows/
  FlowListView.swift      # список сценариев
  FlowCanvasView.swift    # граф уровнями
  FlowNodeView.swift      # узел
  FlowEdgeView.swift      # связь с подписями
  FlowStepDetailView.swift# разбор шага и восстановление
  FlowStepPickerView.swift# добавление из трафика
  FlowLinkEditorView.swift# редактор связи значений
```

`FlowRunner` не зависит от SwiftUI и тестируется отдельно: параллельность, ожидание, условия, каскадный пропуск и восстановление проверяются без интерфейса.

---

## 7. Что не входит

- **Циклы и повторы по коллекции.** Превращает сценарий в язык программирования.
- **Перетаскивание узлов.** Раскладка вычисляется; ручная позиция потребовала бы редактора и хранения координат, не давая ничего взамен.
- **Параллельность внутри одного шага.** Шаг — один запрос.
- **Скрипты на шаге.** Извлечение по JSON-пути закрывает потребность; выполнение произвольного кода в отладочном SDK — отдельный риск.

---

## 8. Риски

| Риск | Смягчение |
|---|---|
| Граф на телефоне быстро становится нечитаемым | Уровни вместо свободной раскладки, провода только между соседними уровнями, дальние зависимости — строкой внутри узла |
| Условия и параллельность превращают фичу в конструктор рабочих процессов | Ветвления только через условие на шаге, без циклов; граф обязан быть ациклическим, проверка при сохранении |
| Сценарий с реальными токенами уходит наружу при экспорте | При экспорте значения заголовков из списка чувствительных заменяются заглушкой; предупреждение в момент экспорта |
| Прогон бьёт по боевому окружению | Сценарий выполняется через активное окружение, оно видно в шапке экрана прогона |
